写程序时，常常需要模型做一个判断：这封邮件该不该转人工，这条查询该不该交给更贵的模型，这个工具该不该被调用。过去常见的做法，是让聊天模型生成一段 JSON，再由代码去解析和校验。Google 11 月 11 日推出的 Gemini Decisions API，针对的就是这类封闭选择。它由新模型 Gemini Decision 1 驱动，不按 token 逐个写出答案，而是在一次前向传播里对给定选项打分，并返回概率和置信度。

一次请求可以提交一份多模态输入，包括文本、图像、音频、视频和 PDF，再附上最多 1,000 道相互独立的是非题、选择题或量表题。官方文档写得更精确：上下文窗口是共享输入和全部问题合计 262,144 个 token，题量还会受这一上限约束。因此，并不能把“输入最多约 256K token”理解成在最大窗口之外还能再叠满 1,000 道题。付费价格为每百万输入 token 0.10 美元，输出不计费，因为输出 token 数始终为 0；共享输入无论问题多少都只计一次，每道题再计入自己的说明和标准。免费层级也可用于原型开发。Google 在博客中称，端到端延迟约为 150–250 毫秒，但同一段说明把这个数字放在上下文不超过 16K token、问题数为 1 到 100 的范围内，不能直接外推到最大窗口或满额题量。

是非题返回“是”的概率，选择题在 2 到 255 个选项中给出归一化概率，量表题则按有序等级给出加权分数。这些问题彼此独立，互不看见对方的题目。官方文档把它和 Interactions API 区分得很清楚：若需要生成文字、按自定义 schema 抽取 JSON，或做多步推理，仍应使用后者。官方列出的典型用途，包括把请求分给不同模型或工具、一次性检查多条策略，以及对候选结果按量表排序。这套接口做的是对已经给出的选项打分，并不是一个可以自行规划、调用工具并完成任务的通用代理。

Google 说，自己已把它用作 Gemini Notebook 的实时路由，并称日常查询的延迟最多可降低约 40%；Search 则用它在时延范围内检测 MCP 工具相关的对抗行为。这些都是公司对内部应用的自述。博客还称，该模型在自建的路由、推理、排序和多模态评测组合上领先，校准误差最低。校准好不好、准不准，取决于具体任务和阈值，并不能从厂商基准直接推广为普遍成立，也不等于用它做安全检查就一定可靠。官方文档也提醒，输入应视为不可信，高风险操作仍需人工或其他复核。

当判断被做成专用接口，它更接近路由或策略检查这类基础设施，而不是又一个聊天窗口。代理要不要行动、怎么行动，仍然要由外层系统决定。这个接口只回答一个更窄的问题：在已经给出的选项里，哪一个更可能成立。
