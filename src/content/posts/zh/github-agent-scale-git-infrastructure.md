GitHub 在工程博客上披露，过去一年 Git 流量呈指数级增长，平台上 99.99999% 的 Git 仓库已经同时存在于两个地方：GitHub 自己的数据中心和微软 Azure。剩下的那一小部分是全站最繁忙的仓库，卡住它们的只有一件事：25 毫秒的往返延迟。

GitHub 说，这次迁移的时机和方式都是被"agent 化转变"推着走的：流量快速增长，自建数据中心及其所在地区的电力容量碰到了硬上限，还有实体供应链的限制。迁移开始时，算上所有可能的扩容，剩余容量足够安全地完成迁移，但不够慢慢来。因此 GitHub 选择先搬数据、再改架构，而不是同时更换存储架构和托管平台。第一个仓库副本在 2025 年 8 月落地 Azure 美国中部区域；如今大多数仓库的五个副本中有两个在 Azure，Azure 承担了大约一半的 Git 流量。这段时间里，增长基本由 Azure 吸收，自建数据中心保持不变。

最后那批仓库的问题出在写入机制上。GitHub 的存储系统 Spokes 只需要多数副本确认就能提交一次写入，但它会等所有健康副本响应（直到超时），而每次写入在提交前都持有整个仓库的锁。于是最慢的那个副本决定了每次写入的延迟，也决定了仓库的吞吐上限。Azure 目标区域距离 GitHub 的数据中心约 1,000 英里，一次往返约 25 毫秒，一次写入又需要多次往返，本来就接近吞吐上限的仓库扛不住。

GitHub 的解法是把仲裁的范围从整个仓库缩小到单个引用（reference）。Git 的一致性要求本来就是按引用计算的，不同分支的更新大多互不依赖。改成按引用串行后，只有争用同一个引用的写入才需要排队，agent 和开发者各自推送自己的分支时就不再互相等待。内部用真实流量测试，写入不同引用的吞吐稳定提升 3 到 4 倍，延迟也更低。

同一步也为读写分离铺了路。大多数仓库每次写入对应 100 到 1,000 次读取。GitHub 正在把 Azure Blob 对象存储作为一个"虚拟副本"加入仲裁，写入要等落盘到对象存储才算确认；之后可以按需扩出任意数量的虚拟读副本，从对象存储预热缓存直接接读流量。GitHub 也承认，下一个瓶颈是写入吞吐，更彻底的架构会在 GitHub Universe 和系列的最后一篇里介绍。

这件事说明 agent 的影响已经传导到了代码托管的底层：不只是多了用户和请求，而是电力、机房和一致性协议都要为 agent 规模的流量重新设计。
